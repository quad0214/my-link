# 마이링크 1단계 시연 PRD

## 1. 문서 목적

이 문서는 마이링크(MyLink)를 단계별로 제작하는 시연의 **첫 번째 구현 범위**를 정의한다. 이번 단계에서는 LocalStorage에 저장된 Mock 데이터를 보여주는 프로필 페이지만 만든다.

관리자 대시보드, 콘텐츠 편집 화면, 통계 수집 및 분석은 이번 단계에서 구현하지 않는다. 이후 단계의 요구사항이 현재 구현 범위를 넓히지 않도록 본 문서를 1단계의 기준으로 사용한다.

| 항목 | 내용 |
| --- | --- |
| 제품명 | 마이링크 (MyLink) |
| 단계 | 1단계 — 프로필 페이지 |
| 대상 사용자 | 개인 사용자, 크리에이터 |
| 구현 형태 | Mock 데이터 + LocalStorage 기반 클라이언트 전용 데모 |
| 상태 관리 | Zustand + `persist` 미들웨어 |
| 디자인 기준 | 프로젝트 루트의 [`design.md`](../design.md) |

## 2. 제품 개요

마이링크는 개인과 크리에이터가 자신의 소개와 여러 외부 링크를 한 페이지에 모아 공유하는 링크 프로필 서비스다.

1단계에서는 이미 프로필을 등록한 사용자 한 명의 Mock 데이터를 준비하고, 방문자가 해당 사용자의 고유 주소로 접속해 소개를 확인하고 외부 링크를 열 수 있는 짧고 반응형인 프로필 페이지를 제공한다.

### 2.1 최종 제품 방향

마이링크의 최종 핵심 흐름은 Linktree 계열 서비스와 동일하다.

1. 프로필 소유자가 계정을 만들고 고유 사용자명을 정한다.
2. 프로필 사진, 이름, 소개를 등록한다.
3. 섹션과 외부 링크를 추가하고 순서를 구성한다.
4. 생성된 `/[username]` 주소를 공유한다.
5. 방문자가 해당 프로필에서 원하는 링크를 선택해 외부 콘텐츠로 이동한다.

현재 1단계는 이 흐름 중 **4~5번에 해당하는 공개 프로필 경험을 먼저 구현**한다. 이후 단계는 프로필·링크 편집, 계정, 통계 순으로 확장한다. 공개 프로필과 링크 이동이라는 중심 경험에서 벗어나는 소셜 피드, 게시물 작성, 메시지, 커뮤니티 기능은 제품 범위에 포함하지 않는다.

- 프로필 사진
- 표시 이름
- 소개
- 섹션 구분 헤더
- 기본 URL 링크 버튼

## 3. 1단계 목표

1. Mock 프로필과 링크 데이터를 LocalStorage에 저장하고 다시 불러온다.
2. 저장 데이터를 모바일 중심의 프로필 페이지로 렌더링한다.
3. 섹션 헤더로 여러 링크를 읽기 쉽게 구분한다.
4. 링크 버튼을 선택하면 올바른 외부 주소를 안전하게 연다.
5. 새로고침 후에도 동일한 프로필 데이터가 유지된다.
6. 이후 편집 기능과 통계를 추가할 수 있는 데이터 구조를 마련한다.

## 5. 사용자 역할 및 시나리오

이번 단계에는 **프로필 소유자**와 **프로필 방문자** 두 역할이 있다. 소유자의 등록·편집 과정은 아직 구현하지 않으며, Mock 데이터가 이미 등록을 마친 소유자의 프로필을 나타낸다.

### 5.1 프로필을 등록한 사용자

**역할:** 자신의 소개와 외부 링크를 하나의 주소로 공유하려는 프로필 소유자

**사전 조건:** `jongcheon` 사용자의 프로필, 섹션, 링크가 Mock 데이터로 등록되어 있다.

1. 프로필 소유자는 자신의 고유 주소 `/jongcheon`을 연다.
2. 앱은 `jongcheon` 프로필에 대응하는 LocalStorage 데이터를 복원한다.
3. 저장 데이터가 없으면 등록 완료 상태를 나타내는 Mock 데이터를 최초 한 번 저장한다.
4. 프로필 소유자는 사진, 이름, 소개, 섹션, 링크가 의도한 순서로 표시되는지 확인한다.
5. 프로필 소유자는 `/jongcheon` 주소를 다른 사람에게 공유한다.

**기대 결과:** 프로필 소유자는 등록된 정보가 하나의 공개 페이지에 정확히 표시되는 것을 확인하고 고유 주소를 공유할 수 있다. 이번 단계에서는 페이지 안에서 정보를 등록하거나 수정하지 않는다.

### 5.2 특정 프로필에 접속한 사용자

**역할:** 공유받은 프로필에서 원하는 채널이나 콘텐츠로 이동하려는 방문자

**사전 조건:** 방문자가 프로필 소유자에게서 `/jongcheon` 주소를 전달받았다.

1. 방문자는 `/jongcheon`에 접속한다.
2. 앱은 프로필 데이터를 복원하는 동안 안정적인 스켈레톤을 표시한다.
3. 방문자는 프로필 사진, 이름, 소개를 확인한다.
4. 방문자는 섹션 헤더를 통해 링크의 주제를 파악한다.
5. 방문자는 원하는 링크 버튼을 선택한다.
6. 앱은 유효한 외부 링크를 `noopener noreferrer`가 적용된 새 탭에서 연다.
7. 기존 프로필 페이지는 현재 상태를 유지한다.

**기대 결과:** 방문자는 특정 사용자의 프로필임을 명확히 이해하고 원하는 링크에 접근할 수 있다. 키보드 사용자도 표시 순서대로 링크를 탐색하고 실행할 수 있으며, 조회수나 클릭 수는 기록되지 않는다.

## 7. 기능 요구사항

### 7.1 초기 Mock 데이터

- 첫 실행 시 Mock 프로필 1개를 제공한다.
- Mock 데이터에는 섹션 헤더 2개와 링크 버튼 4개를 포함한다.
- Mock 데이터는 실제 서비스 데이터처럼 자연스러운 이름과 URL을 사용한다.
- LocalStorage에 유효한 저장 데이터가 있으면 Mock 데이터보다 저장 데이터를 우선한다.
- 저장 데이터가 없을 때만 기본 데이터를 생성한다.
- 매 렌더링이나 새로고침마다 Mock 데이터로 덮어쓰지 않는다.

### 7.2 프로필 영역

- 프로필 사진을 원형 또는 둥근 형태로 표시한다.
- 표시 이름을 페이지의 주 제목으로 표시한다.
- 소개는 최대 160자까지 자연스럽게 줄바꿈한다.
- 프로필 사진이 없거나 로드되지 않으면 표시 이름의 첫 글자를 사용한 기본 아바타를 표시한다.
- 긴 이름과 소개가 작은 화면에서 잘리거나 가로 스크롤을 만들지 않아야 한다.

### 7.3 콘텐츠 블록

프로필 본문은 저장 순서가 있는 두 종류의 블록으로 구성한다.

#### 섹션 헤더

- 관련 링크 그룹의 시작을 알리는 텍스트다.
- 링크 버튼보다 낮은 시각적 강조를 사용한다.
- `visible`이 `false`이면 표시하지 않는다.

#### 링크 버튼

- 링크 제목을 표시한다.
- 버튼 전체 영역을 선택할 수 있어야 한다.
- `https://` 또는 `http://` URL만 허용한다.
- 외부 링크는 새 탭에서 연다.
- `noopener noreferrer`를 적용한다.
- `visible`이 `false`이면 표시하지 않는다.
- 유효하지 않은 URL은 버튼으로 표시하지 않는다.

### 7.4 빈 상태와 오류 상태

- 공개 링크가 하나도 없으면 “아직 등록된 링크가 없어요.”라는 간단한 빈 상태를 표시한다.
- LocalStorage를 사용할 수 없어도 기본 Mock 프로필은 현재 세션에서 볼 수 있어야 한다.
- 저장 데이터가 손상되었으면 앱이 중단되지 않아야 한다.
- 손상된 데이터를 자동으로 덮어쓰지 않고 현재 세션에서 기본 Mock 데이터를 사용한다.
- 오류 세부 정보나 스택 트레이스를 사용자 화면에 노출하지 않는다.

## 8. 데이터 모델

```ts
type Profile = {
  username: string;
  displayName: string;
  bio: string;
  avatarUrl: string | null;
};

type SectionBlock = {
  id: string;
  type: "section";
  title: string;
  visible: boolean;
};

type LinkBlock = {
  id: string;
  type: "link";
  title: string;
  url: string;
  visible: boolean;
};

type ContentBlock = SectionBlock | LinkBlock;

type ThemePreference = "light" | "dark" | "system";

type MyLinkStore = {
  version: 1;
  profile: Profile;
  blocks: ContentBlock[];
  theme: ThemePreference;
  updatedAt: string;
};
```

통계 필드와 방문 기록은 1단계 데이터 모델에 포함하지 않는다.

## 10. Zustand 및 LocalStorage 설계

### 10.1 스토어 상태

`useMyLinkStore` 단일 스토어는 다음 상태만 관리한다.

- `profile`
- `blocks`
- `theme`
- `hasHydrated`

`hasHydrated`는 LocalStorage 복원 여부를 나타내는 실행 상태이며 영속 저장하지 않는다.

### 10.2 영속화 규칙

- 스토리지 키는 Mock 사용자명을 포함한 `mylink:profile:jongcheon:v1`을 사용한다.
- 스토어 버전은 `1`로 지정한다.
- `profile`, `blocks`, `theme`만 저장한다.
- 액션 함수와 `hasHydrated`는 저장 대상에서 제외한다.
- 데이터 구조 변경에 대비해 `version`과 `migrate`를 사용할 수 있는 구조로 작성한다.
- 컴포넌트가 LocalStorage를 직접 수정하지 않도록 저장 책임을 Zustand 스토어에 둔다.

### 10.3 Next.js Hydration

- 서버 렌더링 중 `window`와 LocalStorage에 접근하지 않는다.
- 클라이언트 마운트 이후 저장 상태를 복원한다.
- 복원이 끝날 때까지 안정적인 스켈레톤을 표시한다.
- 저장 상태 복원 전에 Mock 데이터 화면을 순간적으로 표시했다가 바꾸는 깜빡임을 만들지 않는다.
- 서버 HTML과 클라이언트 첫 렌더링의 구조를 동일하게 유지한다.

## 11. 디자인 요구사항

프로필 페이지는 [`design.md`](../design.md)의 시각·행동 원칙을 기준으로 한다.

실제 제품 화면에는 삼성·Galaxy·One UI 명칭, 로고, 상표, 저작권 문구, 출처 또는 디자인 시스템 안내를 표시하지 않는다. 코드의 사용자 노출 문자열과 클래스명에도 해당 명칭을 사용하지 않는다.

### 11.1 화면 구성

- 상단 뷰잉 영역에 프로필 사진, 이름, 소개를 배치한다.
- 링크가 있는 인터랙션 영역은 그 아래에 배치한다.
- 프로필 정보와 링크 목록 사이에 충분한 공간과 명확한 위계를 둔다.
- 별도 내비게이션, 대시보드 진입 버튼, 통계 요약 카드를 배치하지 않는다.
- 한 화면에서 과도한 장식과 여러 버튼 스타일을 혼용하지 않는다.

### 11.2 색상과 형태

- 역할 기반 색상 토큰을 사용한다.
- 주요 인터랙션은 디자인 가이드의 Primary 계열을 사용한다.
- 큰 표면에는 20~26px, 작은 요소에는 12px 반경을 기준으로 사용한다.
- 인접 터치 대상 사이 간격은 최소 8px을 유지한다.
- dim과 shadow를 같은 요소에 동시에 적용하지 않는다.

### 11.3 반응형

- Compact, 600px 미만: 한 열 레이아웃과 최소 24px 좌우 여백을 기본으로 한다.
- Medium, 600~839px: 프로필 콘텐츠의 읽기 폭을 유지하며 여백을 확장한다.
- Expanded, 840px 이상: 모바일 카드를 과도하게 늘리지 않고 적절한 최대 너비로 중앙 정렬한다.
- 최소 360px 화면에서 가로 스크롤이 발생하지 않아야 한다.

### 11.4 테마

- 라이트·다크 테마를 모두 지원한다.
- 기본값은 시스템 설정을 따른다.
- 별도 설정 화면은 만들지 않는다.
- 페이지 내 간결한 테마 전환 컨트롤은 선택 사항이다.
- 선택한 테마가 있다면 LocalStorage에 저장한다.

## 12. 접근성 요구사항

- 모든 링크를 키보드로 탐색하고 실행할 수 있어야 한다.
- 포커스 순서는 화면에 표시된 순서와 일치해야 한다.
- 포커스 상태는 색상 외 윤곽선으로도 표시한다.
- 링크 버튼은 목적지를 이해할 수 있는 접근 가능한 이름을 가진다.
- 프로필 이미지에는 의미 있는 대체 텍스트를 제공한다.
- 작은 일반 텍스트는 배경 대비 4.5:1 이상을 만족한다.
- 색만으로 링크 상태나 오류를 표현하지 않는다.
- 브라우저 텍스트 200% 확대에서도 콘텐츠와 기능이 손실되지 않아야 한다.
- `prefers-reduced-motion`이 활성화되면 필수적이지 않은 움직임을 제거한다.

## 13. 비기능 요구사항

### 성능

- 초기 렌더링에 불필요한 외부 요청을 만들지 않는다.
- 첫 화면에 필요한 코드와 자산만 사용한다.
- 레이아웃 이동 없이 프로필 콘텐츠가 표시되어야 한다.

### 개인정보

- 프로필 데이터는 사용자의 브라우저에만 저장한다.
- 서버 전송, 쿠키 기반 추적, 외부 분석을 사용하지 않는다.
- 조회와 클릭 이벤트를 수집하지 않는다.

### 호환성

- 최신 Chrome, Edge, Safari, Firefox를 지원한다.
- LocalStorage를 사용할 수 없는 환경에서도 읽기 전용 프로필 화면을 제공한다.

## 15. 후속 단계

후속 기능은 별도 PRD 또는 본 문서의 다음 버전에서 한 단계씩 정의한다.

1. 프로필 및 링크 편집 화면
2. 블록 추가·삭제·순서 변경
3. 관리자 대시보드
4. 프로필 조회수와 링크 클릭 통계
5. 실제 인증과 사용자별 프로필 생성 및 조회
6. 서버 저장과 여러 기기 동기화

후속 단계가 승인되기 전에는 해당 기능을 미리 구현하지 않는다.
